## Alarm Clock

#### DATA STRUCTURES

>A1: Copy here the declaration of each new or changed struct or struct member, global or static variable, typedef, or enumeration.  Identify the purpose of each in 25 words or less.

`struct thread`

```c
int64_t wakeup_tick;
```

Stores the earliest timer tick at which a blocked sleeping thread may be unblocked.

`devices/timer.c`

```c
static struct list sleep_list;
```

Ordered list of threads blocked in `timer_sleep()`, sorted by `wakeup_tick` and then priority for same-tick wakeups.


#### ALGORITHMS

>A2: Briefly describe what happens in a call to timer_sleep(),
>including the effects of the timer interrupt handler.

If the requested sleep duration is zero or negative, `timer_sleep()` returns immediately. Otherwise it disables interrupts, records the current thread's `wakeup_tick`, inserts the thread into `sleep_list` in wake-up order, and calls `thread_block()`. Every timer interrupt increments the global tick counter, checks the front of `sleep_list`, and unblocks every thread whose `wakeup_tick` has arrived.


>A3: What steps are taken to minimize the amount of time spent in
>the timer interrupt handler?

`sleep_list` is kept sorted when threads go to sleep, so the interrupt handler only looks at the front of the list. It stops as soon as it finds a thread whose wake-up tick is still in the future, avoiding a full scan on every tick.


#### SYNCHRONIZATION

>A4: How are race conditions avoided when multiple threads call
>timer_sleep() simultaneously?

`timer_sleep()` disables interrupts before it writes the current thread's wake-up tick, inserts the thread into `sleep_list`, and blocks. This makes each insertion atomic with respect to other threads on a uniprocessor Pintos kernel.


>A5: How are race conditions avoided when a timer interrupt occurs
>during a call to timer_sleep()?

The timer interrupt cannot run while `timer_sleep()` is modifying `sleep_list`, because interrupts are disabled around the critical section. The thread is inserted before it blocks, so once interrupts are restored it is either already blocked safely or ready to be woken by a later timer interrupt.


#### RATIONALE

>A6: Why did you choose this design?  In what ways is it superior to
>another design you considered?

An ordered sleep list keeps sleeping threads blocked instead of repeatedly yielding, so it avoids busy waiting. Sorting at insertion time costs O(n) only when a thread goes to sleep, while each timer interrupt usually performs O(1) work. A simpler unsorted list would make `timer_interrupt()` scan every sleeping thread on every tick, increasing interrupt latency as the number of sleepers grows.
